金融Fin-agent项目开发版本迭代实录

一份从「一句需求」到「一个能跑的 A 股投研 Agent」的完整施工记录。
面向博客读者：每个阶段都按 问题 → 为什么这么想 → 解决思路 → 最终方案 → 结果 拆开写，
保留走过的弯路和被推翻的判断。

0. 先说清楚这是什么

FinancialAI-Agent 是一个面向 A 股的智能投研 Agent：用大白话提问，它自己规划、
调用行情工具、算指标、写结论，并且在把结论交给你之前，先过三道关。

  • 3 个 Agent：研究（查行情/读财报/筛股票）、量化（回测/持仓）、预警（价格提醒/资金流）
  • 41 个工具：按职责拆成 market / quant / portfolio 三个独立 MCP 服务
  • 4 道关：逻辑审查（LLM）→ 证据校验（确定性代码）→ 风控硬规则 → 交付
  • 672 个测试：全部离线可跑，不需要 API Key，不需要联网
  • 界面：SSE 流式、工具调用时间线、断线重连、敏感操作审批

仓库：https://github.com/CPLASF2049/FinancialAI-Agent

跑起来只要三行：

pip install -e ".[dev]"
cp .env.example .env      # 默认已连东方财富，免费、不需要 key
finagent web              # http://127.0.0.1:8000

下面开始讲它是怎么一步步变成这样的。

1. 起点：一句模糊的需求

问题

最初的原始项目是 GitHub 上一个小的金融分析 demo。需求只有六个字：

「把这个改造成 mcp+langgraph 的项目」

没有验收标准，没有设计文档，也没说要做成什么样。

为什么这么想

一个改造类需求，最容易踩的坑是「换个包装就当改造完了」。所以在动手之前，
先问了一个问题：MCP 到底解决了什么？

如果答案只是「把函数换个方式注册」，那这次改造没有价值——多一层协议，
只是多一层故障点。

我们给出的判断是：MCP 的价值是「工具面可替换」。
数据源从离线 fixture 换成 Tushare、再换成东方财富，上层 41 个工具一行都不用改。
这才是值得付协议成本的理由。

解决思路

有三条路：

  1. 按专家切图：每个专家一个子图，专家之间互相调用
  2. 按步骤切图：取数 → 分析 → 审查 → 交付
  3. Supervisor 编排：一个调度节点决定「下一步谁干活」，专家之间不互相调用

第 1 条的问题是耦合：专家 A 要改，得知道专家 B 的输入输出格式。
第 2 条的问题是僵硬：金融问题常常需要回退（数据不够就再查一次），线性的图不好表达。
第 3 条把「谁下一步干活」收敛到一个地方，专家只负责自己的事。

最终方案

  • 工具层抽象成 Provider 接口，工具只依赖接口，不依赖具体数据源
  • 图用 StateGraph，Supervisor 用 Command(goto=...) 做路由
  • 三个专家节点，各自有互不重叠的工具白名单（PASS_TOOLS）
  • 状态里带 completed_agents / agent_hops，防止重复派发

结果

这个判断后来救了整个项目：数据源被封、被限流、换供应商，都只是换一个 provider
实现，上层零改动。

2. 真实数据：从 fixture 到东方财富

问题

第一版能跑，但数据是离线 fixture。用户的要求很直接：

「第一步：强制启用真实数据 Provider……我要的是真实的数据跑起来」

为什么这么想

演示数据和真实数据的差别不是「真假」，而是脏。真实数据会：

  • 缺字段（某些股票没有行业分类）
  • 有时延（收盘后一段时间才更新）
  • 会限流（连续请求直接被断连）
  • 格式不统一（万元/元、手/股、是否有复权）

用 fixture 写的代码，上线第一天就会崩。

解决思路

三条路：买 Tushare 的 token、爬付费接口、找不需要 key 的公开接口。

我们选了第三条：东方财富的公开行情接口。免费、免注册、数据是真的。

代价是这类接口不稳定——但这个代价是可以工程化处理的，而「没有 token 就跑不了」
是无法工程化处理的。

最终方案

  • EastmoneyProvider：日线、实时报价、估值、指数、全市场选股池
  • 字段统一到一套口径（ts_code、万元、手），上层不用感知数据源
  • 磁盘缓存合并：全市场列表一次抓不完就分页追加，下次接着用
  • 完整性标记：last_universe_complete / last_universe_source

结果

真实数据跑通了。然后立刻遇到了下一个问题。

3. IP 被封：备用源与「降级要说实话」

问题

跑了几轮全市场选股之后，东方财富开始返回 RemoteDisconnected。
排查发现：K 线接口还活着，但报价和列表接口全死——典型的按接口限流/封禁。

为什么这么想

这时候有个诱人的捷径：接口失败就返回空结果。界面不报错，用户以为「今天没数据」。

这是最危险的做法。金融场景里，假阴性比报错危险得多：
按行业筛银行股，返回空列表会让用户以为「银行股都不满足条件」，
而真相是「我们没拿到行业字段」。

所以定下一条原则：降级必须说实话。

解决思路

  1. 加备用源：新浪的实时报价和全市场列表
  2. 字段口径对齐到同一套，上层不感知切换
  3. 拿不全时明确标注，而不是假装拿全了

最终方案

情况 做法
只拿到部分市场 标 universe_complete=false + warning，绝不把「命中 N 只」当全量
备用源没有行业分类 按行业筛直接报错，并提示「可用 mx_stock_screen」
两个源都挂 抛 ProviderUnavailable，带可操作 hint

结果

这条原则后来贯穿到整个项目：部分成功、证据等级、终止原因，都是同一个思路的延伸——
失败要有名字，不能沉默。

4. 审查者瞎报：命名空间与「与事实对账」

问题

用户贴回来一段日志：

「本轮专家未调用任何工具，结论中 24 只标的……均无工具返回依据」

但同一个界面上明明显示 ✓ screen_stocks 成功了。

后果是致命的：审查者每次都判定「结论没有依据」→ 专家返工 → 再来一遍 →
再被判无依据。token 翻倍，时间翻倍，结论还是一样。

为什么这么想

第一反应是「模型在瞎说」。但去看 trace 之后发现，模型说的其实是它看到的事实——
它拿到的记录里，agent 字段是 researcher:screening，而过滤条件是 researcher。

精确匹配，永远匹配不到。

这类 bug 最难查的地方在于：它不报错。日志里每一行都很合理：
「审查完成，判定返工」——单看每一条都对，连起来就是死循环。

解决思路

  1. 修命名：trace 记录用裸 agent 名，子职责放到独立的 stage 字段
  2. 加前缀兜底：researcher:screening 也能匹配 researcher
  3. 更根本的一条：审查意见必须和事实对账

第 3 条是这次事故最大的收获。模型说「没调工具」，但记录里有 4 次调用——
这条意见直接作废。模型说「15/16 个数字没出处」，但规则核对显示 90% 有出处——
也作废。

定性判断仍然听模型的；事实性判断必须和记录对账。

最终方案

  • reconcile()：在规则审查和模型审查之间对账，丢弃被事实推翻的意见
  • 规则先跑，模型只补充规则覆盖不到的部分
  • 代码验证不复用模型生成的代码：只允许注册表里的策略 ID，
    用子进程按 spec 重跑一遍再比对指标

结果

同一个问题：370 秒 + 2 次返工 → 138 秒 + 0 次返工。

5. 卡死烧 Token：蹦不出字（整个项目最痛的一章）

「AI 一直卡死、消耗大量 Token 却跑不出结果」
「当时特别关键，蹦不出字」

问题

用户看到的永远是同一个画面：光标在转，什么都没有，等 3 分钟，
要么空白，要么突然冒出一大段。而账单上 token 已经烧掉几万。

最要命的是：三种完全不同的病，表象一模一样。

表象 真实情况 用户以为
白屏 30–90 秒后突然出字 模型在思考，token 在生成，但只显示 content 卡死了
白屏 2 分钟以上，最后超时 专家内部循环失控，一个工具反复失败反复重试 网络问题
出字了又被打回，反复重写 审查者误判，触发无限返工 模型太笨

三种混在一起，用户没法判断该等、该刷新、还是该改问法。

为什么这么想

排查时先做了一件反直觉的事：不接受「卡住」这个描述。

「卡住」是现象，不是原因。所以把它拆成三个可观测的问题：

  1. 模型到底有没有在生成？（看 token 用量曲线）
  2. 如果有，为什么界面没有？（看事件流）
  3. 如果事件流也没有，是谁没发？（看发射点）

拆完发现是五个独立的洞，只是恰好同时出现。

解决思路

按「先止血、再治本、最后给可见性」的顺序，而不是一次全改：

  1. 止血：让最极端的情况先停下来（预算）
  2. 治本：让停下来这件事可解释（终止原因枚举）
  3. 可见性：让用户知道它在动（流式 + 阶段事件 + 心跳）

最终方案：五道防线

第一道 · 四重预算，穿透到最内层

Budget(max_llm_calls=15, max_tool_calls=40, max_retries=2, timeout_seconds=180)

关键不是「有预算」，而是检查点在哪：在 AgentRuntime 每一轮循环开头，
也就是模型调用之前、工具执行之前——最内层。

def _preflight(self, iteration, outcome):
    if self.is_cancelled():               return "cancelled"
    if time.monotonic() > self.deadline:  return "deadline"
    if self._tokens > self.token_budget:  return "budget_tokens"
    if self.stats.total >= max_tool_calls: return "budget_tool_calls"

顺序固定：取消 > 时间 > token > 次数。越靠前越紧急。

第二道 · 终止原因是枚举出来的

submit / budget_iterations / budget_tokens / budget_wallclock
tool_failure / no_progress / model_failure / contract_violation / cancelled

「做完了」和「预算耗尽」是两件事。前者交付完整结论，后者交付部分结果 + 说明。

第三道 · 无进展守卫 + 返工预算

进展指标一开始写错了：用「累计工具调用数」，一直失败一直重试也会让它增长，
恰好识别不出「烧 token 没结果」的形态。改成只看成功调用 + 文本长度：

progress = stats.succeeded + len(text)
if progress <= last_progress:
    stall += 1
    if stall >= 2: 停

第四道 · 空回复不算完成

这条是后来才发现的，也是最讽刺的一条：模型返回空内容时（不带 tool_calls），
旧逻辑直接 stopped_reason = completed、text 为空——界面看起来「跑完了」，
实际什么都没有。

这就是用户说的「蹦不出字」本身。现在：空回复先重试一次，仍为空则
model_failure，并给一句可读说明。

第五道 · 等待必须有反馈

  • token 事件：每吐一个字推一次 SSE
  • 阶段事件：step:start / tool:* / critic 告诉用户在干什么
  • 心跳：15 秒没有新事件就 ping，前端据此判断连接

结果

指标 修之前 修之后
典型一轮耗时 370 秒 138 秒
返工次数 2 次 0 次
首字出现 20–90 秒（或永远不来） 模型开始输出的第一刻 + 阶段事件兜底
失败可见性 无 终止原因 + 事件表

这一章留下的四条教训

  1. 预算必须穿透到最内层循环。 只在顶层检查等于没有。
  2. 参数存在 ≠ 参数生效。 曾经 deadline 参数加了、逻辑写了、测试过了，
    唯独调用点没传。要测「超时一定停」，不要测「函数收到 deadline」。
  3. 没有终止原因的失败，等于没法排查。
  4. 等待必须有反馈。 用户受不了的不是慢，是不知道还要不要等。

6. 界面点不动、空对话堆积

问题

「总是出现按钮点不动了，刷新之后发现新对话很多了几个空对话」

为什么这么想

两个现象看起来无关，其实是一条因果链：

流卡住 → 用户以为没反应 → 连点「新建对话」→ 每次点击都 POST 一个会话 → 堆一排空会话。

而按钮点不动的直接原因，是 SSE 流卡住时前端没有超时机制，
state.streaming 永远是 true，「发送」被永久禁用。

解决思路

  • 前端加看门狗：2 分钟没有任何输出就主动收尾，把界面还给用户
  • 「新建对话」不再每次 POST
  • 心跳事件让前端能判断连接是否还活着

最终方案

后来这套方案被用户推翻了，因为更符合直觉的做法是：

点「新建对话」就建一条空会话，但没说过话就切走要自动删掉。

于是最终形态：

行为 实现
新建 → 建空会话 立刻 POST，切走再切回还在
没说话就切走 DELETE ?if_empty=1，只删空的
发过内容 → 固定 一旦发送就不再是 draft
标题 从首条内容提炼（去寒暄前缀、去尾标点、截 24 字）

结果

这条经历说明：需求会反向修正设计。
第一版为了防堆积而「不建会话」，其实是牺牲了用户的心理模型。

7. 2.0：把执行骨架重做一遍

用户给了一份完整的架构评审，六个 P0/P1 项。这不是加功能，是重做骨架。

P0-1 Provider 层：能力注册中心 + 策略网关

问题：限流、断连、超时、空数据，四类故障在每个工具里各写一遍，口径不一。

为什么这么想：这些是数据源的共性，不是某个工具的特性。放在工具里，
41 个工具就有 41 套重试逻辑。

解决思路：

  • 通道层：重试、退避、熔断、降级（provider 之间）
  • 网关层：缓存、并发合并、超时（与具体数据源无关）

最终方案：

PROVIDER_CAPABILITIES = {"eastmoney": {"daily", "realtime", ...}, ...}
CallResult = SUCCESS | PARTIAL_SUCCESS | PROVIDER_UNAVAILABLE

熔断（连续失败 → 冷却 30s）、缓存（快照 5s / 日线 60s / 选股池 300s）、
singleflight（并发合并）、三态返回。

结果：41 个工具一行没改，全都获得了这些策略。
同时暴露一个隐藏问题——FinAgentError.code 是类属性，没法按场景区分错误码，
于是扩展成实例级 code / retryable / provider。

P0-2 统一工具执行管线

问题：日志里出现过「连续 4 次工具失败」和「错误=0」同时出现。

为什么这么想：失败计数和错误列表是两套变量，各数各的。

解决思路：所有工具走同一个执行器，统计从执行结果派生，不手工累加。

最终方案：ToolResult（状态/错误码/可重试/耗时）+ ToolStats
（total / succeeded / partial / failed / unsupported / skipped / retries）。

关键区分：unsupported 不算失败。它是能力边界（当前数据源没这项能力），
重复出现不该触发刹车。

结果：日志变成「工具=10[成功6/失败3/不支持1/重试2]」，不再自相矛盾。
实现时还踩了个坑：MCP 适配器返回的是 [{"type":"text","text":...}] 这种
content-block 列表，不处理会把错误信封当成成功文本。

P0-3 独立的证据校验器

问题：审查者是语言模型，能判断「这段话顺不顺」，判断不了「32.25 是不是今天的收盘价」。

为什么这么想：模型可能真诚地说「15/16 个数字有出处」——它真的这么认为。

解决思路：把「数字对不对」从模型手里拿走，用确定性代码做三件事：

  1. 数字能否在工具返回里找到出处
  2. 区间涨幅能否用首尾价重算
  3. 数据时点是否过期

最终方案：五种证据等级 VERIFIED / PARTIALLY_VERIFIED / UNVERIFIED / CONFLICTED / STALE，
只有前两种允许当「确定数字」发布。

踩的坑（都是"看起来能跑、算出来是错的"）：

  • 日期 20261001 被当成价格，区间涨幅算成 -100%
  • 百分比拿去和「元」的数字池比对，30% 命中 30.0 元，误判为已验证

结果：模型算错涨幅会被立刻拦下。

P1-4 统一执行循环 + 三层上下文

问题：每个专家各写一套「模型→工具→模型」循环，预算和压缩各实现一遍。

为什么这么想：循环是共性，差异只在 prompt 和工具白名单。

最终方案：AgentRuntime 统一循环；上下文分三层：

层 内容 压缩策略
core 用户目标、约束 永不压缩
summary 专家结论、证据引用 折叠成一条
detail 工具原始返回 最先压缩成引用 + 摘要

压掉的原文登记在 context.references——压缩不等于丢失。

P1-5 三模块边界 + 部分成功

问题：任何一项数据失败，整段结论都可能被写成「数据不可用」，
用户连已经拿到的价格都看不到。

为什么这么想：一刀切的失败是最省事的失败，也是最没用的失败。

最终方案：请求拆成必做 / 可选子任务。

必做项全满足 → complete
必做项部分缺失 → partial，正文末尾写「缺少：近期走势」
可选项失败 → 不影响交付，只提一句「未覆盖」

踩的坑：走势最初被「单次报价」满足，导致只查了现价也判 complete——
走势必须有价格序列，已修正并加测试。

P1-6 后台运行与断线重连

问题：

「生成过程中切换到别的对话后，这个对话就不生成了，回来之后变成一片空白」

为什么这么想：执行的生命周期挂在 HTTP 请求上，客户端一断，执行就死。

最终方案：执行与投递解耦。

run（后台任务） → 缓冲（可重放） → 订阅者
  • 断开只结束投递，后台继续跑
  • 重连带 after=<seq> 续播，不重跑
  • 心跳 15 秒

实现时修了个通知竞态：asyncio.Condition 的 notify 早于 wait 注册会丢，
表现为「重连后卡住」。改成显式 waiter 列表。

结果：连接只读两行就断开，3 秒后后台已跑完（33 个事件、状态 done），
重连补发 8090 字节含 done。

8. 前端：先重做，再回滚

问题

用户给了一份非常具体的设计规范（Claude Code 风格），核心是「可观察的自主性」。

为什么这么想

上 React 需要构建链。项目原本是零构建的静态 HTML/JS。两条路：

  • CDN + Babel standalone：不用构建，但依赖 CDN 可达、首屏要等编译
  • Vite + Tailwind：需要 package.json，但产物是静态文件，部署不用装 Node

最终方案（第一版）

选了 Vite：31 个模块、JS 159KB（gzip 51.8KB）、1.6 秒构建。
权限审批做成了真的后端闸门——工具执行前挂起等 future，拒绝就不执行。

结果

几天后用户要求回滚。

「前端页面直接回滚，不需要这个样子了，回到原来的样子」

这不是失败，是 Vibe Coding 的真实一部分：设计规范写得再好，
也不等于日常使用顺手。 终端风格适合长时间盯日志，不适合随手问一句「茅台多少钱」。

回滚时顺手修了一个真 bug：经典界面里

provider === "tushare" ? "Tushare 行情" : "离线演示数据"

只判断了一个分支，于是 eastmoney 的真实行情一直被标成「离线演示数据」。
用户提了好几次「离线演示数据不要出现」，根因是这一行。

教训：用户反复报同一个问题，说明我们一直在修错的地方。

9. 外部视角：当别人拿这个项目写简历

问题

有人在另一个对话里拿这个项目写简历，写了科研 / Agent 开发 / 量化三个版本。

为什么值得记

一个人会怎么向别人介绍你的项目，暴露了你的重心在哪。

它挑中的卖点

方向 挑中的机制
科研 「确定性基线 + LLM」双模式，可作对照组
工程 MCP 三层解耦 + 有状态编排 + 决策轨迹可观测
量化 回测引擎 + 选股器 + 风控规则

没有一个版本把「多 Agent 协作」当核心卖点。理由是：

不要只写「做了多 Agent」，要写清楚哪个机制能被单独开关、用来度量什么。

它逼出的差距

顺着「可消融」推，最自然的因子是 Critic、RiskGuard、离线模式。
前两个我们没做成开关，审查链是写死的——所以能说「有审查」，
说不清「审查带来多少改善」。

它暴露的滞后

那个对话里写的是「6 个专家、352 个测试」，当前仓库是「3 个 Agent、672 个测试」。

对外材料比代码滞后了一个大版本。 教训：写进对外材料的数字，
必须能用一条命令复现。

10. 方法论：可以复用的部分

每次修 bug 的三步

  1. 复现——本地跑一遍，不靠猜
  2. 找根因——不是「看起来像什么」，是「哪一行导致的」
  3. 加测试——修完必须有一条用例钉住

这份记录里大部分「故障」，最后都变成了 tests/ 下的一个文件。

五个判断，事后看是对的

  1. Provider 抽象——救了后面所有数据源问题
  2. 降级说实话——假阴性比报错危险
  3. 数字交给代码算——模型算涨跌幅一定会错
  4. 预算穿透到最内层——只在顶层检查等于没有
  5. 审查意见要和事实对账——模型会编理由，记录不会

四个判断，事后看是错的

  1. 以为「不建空会话」能解决堆积——牺牲了用户直觉
  2. 以为预算参数加上就生效——写了没人传
  3. 以为改完代码用户就能看到——没重启进程，用户看的一直是旧版本
  4. 以为测试覆盖就等于对了——「日期当价格」这种 bug，不写用例发现不了

一条贯穿始终的原则

失败要有名字。

  • 数据源降级 → universe_complete=false
  • 证据不足 → UNVERIFIED / CONFLICTED / STALE
  • 执行结束 → submit / budget_tokens / no_progress / model_failure
  • 部分交付 → partial + 「缺少：近期走势」

没有名字的失败，只是一个黑洞。用户看不懂，自己也查不动。

指标 数值

所有数字都能用一条命令复现：

python -m pytest -q          # 672 passed
curl /api/info               # tool_count / experts / build
python scripts/eval_suite.py # 评测集

写在最后

这个项目不是一次设计出来的。它是被一系列具体故障推着长大的：

IP 被封 → 有了备用源和「降级说实话」；
审查者误判 → 有了「与事实对账」；
卡死烧 token → 有了预算穿透和终止原因；
数字被编 → 有了证据校验；
切走就白跑 → 有了后台执行；
前端重做又回滚 → 有了「用户顺手比设计规范重要」。

每一次都是先被咬一口，才长出那块骨头。

如果这篇实录只能留下一句话，我想是这句：

不要相信「看起来在跑」，要让它说出自己在跑什么、跑到哪、为什么停。
